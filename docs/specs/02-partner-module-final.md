**BoomCard**

**Партньорски модул \- финална техническа спецификация**

**1\. Процес на движение на партньора**

| Етап | Статус / label | Какво се случва | Достъп |
| :---- | :---- | :---- | :---- |
| 1 | New (Нова заявка) | Кандидатът изпраща форма. Създава се запис в admin панела. | Няма достъп |
| 2 | Комуникация | BoomCard инициира контакт и поема заявката. | Няма достъп |
| 3 | Договаряне | Обсъждат се условия, локации, участие и договорни параметри. | Няма достъп |
| 4 | Onboarding | Създава се партньорски запис. Събират се данни, съдържание, локации, QR и примерни бележки. | Няма login достъп |
| 5 | Active | Профилът е валидиран, локациите и QR кодовете са готови. Изпраща се activation линк. | Има достъп |
| 6 | Пауза → `Inactive` | Временно ограничаване на видимостта или работата (временна оперативна пауза). Мapва се към `Inactive` в каноничния enum. Партньорът запазва read-only достъп; нови транзакции са блокирани. | Read-only достъп |
| 7 | Спрян → `Inactive` | Партньорът е деактивиран по решение на admin (наложено спиране). Mapва се към `Inactive` в каноничния enum, с reason/sub-type поле, указващо причината за спирането. Поведението в системата е идентично с Пауза. | Read-only или без достъп според admin настройка |
| 8 | Архивиран | Исторически запис без активна оперативна роля. Реактивирането е възможно само чрез admin action, което задейства нов onboarding review. QR кодовете не се реактивират автоматично — Admin трябва изрично да реактивира всеки QR код. | Няма активна роля |
| 9 | Rejected | Заявката е отказана преди активиране. | Няма достъп |

| Mapping бележка: "Пауза" и "Спрян" са оперативни UI labels, използвани в BoomCard за комуникация с екипа. И двата label-а се mapват към канонична стойност `Inactive` в базата данни и в API-то (`partner_account_status = Inactive`). Разграничението между временна пауза и admin-наложено спиране се пази в отделно поле `reason` / `sub_type`, НЕ чрез разширяване на каноничния enum. Каноничният enum (`Active | Inactive | Archived`) не се разширява. Вижте Unified Spec §1.4 Partner Account Lifecycle. |
| :---- |

| Правило: Статусите трябва да бъдат еднакви като логика във frontend, backend, admin панела, notifications и справките. |
| :---- |

**2\. Форма за кандидатстване**

| Секция | Поле | Статус | Поведение |
| :---- | :---- | :---- | :---- |
| Лична информация | Име | Задължително | Контактно лице |
| Лична информация | Фамилия | Задължително | Контактно лице |
| Лична информация | Имейл | Задължително | Потвърждение и бъдеща комуникация |
| Лична информация | Телефон | Задължително | Контакт |
| Бизнес информация | Име на бизнес | Задължително | Влиза в партньорската заявка |
| Бизнес информация | Категория | Задължително | Multi-select |
| Бизнес информация | Подкатегория | Задължително | Multi-select |
| Бизнес информация | Град | Задължително | Основен град |
| Обект | Адрес | Задължително | Основна локация или първи обект |
| Обект | Брой обекти | Задължително | Dropdown |
| Квалификация | Ниво на участие | Задължително | Базово участие / Активно участие / Силен растеж |
| Допълнително | Свободен текст | Незадължително | Допълнителен контекст |
| Съгласия | Общи условия | Задължително | Submit не се допуска без това |
| Съгласия | Политика за поверителност | Задължително | Submit не се допуска без това |
| Съгласия | Маркетингов консент | Незадължително | Може да се включва или изключва по-късно |

* Формата не създава логваем акаунт.  
* Формата не съдържа поле за парола.  
* След submit се създава запис със статус New (Нова заявка).  
* Партньорът не получава достъп до панел преди завършен onboarding.

**3\. Действия след изпращане**

| Действие | Какво трябва да стане | Къде се вижда |
| :---- | :---- | :---- |
| Създаване на запис | Създава се партньорска заявка със статус New (Нова заявка). | Admin: Партньори \> Заявки |
| Визуално потвърждение | Кандидатът вижда съобщение, че заявката е изпратена успешно. | Сайт / форма |
| Вътрешна обработка | Заявката получава дата, статус, история и поле за отговорник. | Admin панел |
| Външно обещание | Кандидатът може да бъде информиран за контакт до два работни дни. | Сайт / confirmation message |
| Вътрешен SLA | Екипът трябва да поеме заявката в рамките на 24 часа. | Admin task / вътрешна логика |
| Login restriction | Не се показва login екран и не се създава достъп за Pending запис. | Frontend / auth logic |

**8\. Какво съдържа всяко меню**

**8.1 Табло**

| Елемент | Какво се вижда | Действие | Ограничение |
| :---- | :---- | :---- | :---- |
| KPI карти | Брой посещения, брой транзакции, оборот, договорен процент, очаквани суми. | Само преглед | Данните идват от транзакции, локации и финанси. |
| Последна активност | Последни транзакции или последни отчетни промени. | Само преглед | Без редакция. |
| Финансов summary | Очаквани суми за фактуриране и текущ financial status. | Само преглед | Без показване на вътрешен margin или cashback formula. |

**8.2 Транзакции**

| Елемент | Какво се вижда | Действие | Ограничение |
| :---- | :---- | :---- | :---- |
| Списък с транзакции | Transaction ID, дата, час, локация, сума, процент, отстъпка, статус. | Преглед и филтриране | Без редакция, одобрение или изтриване. |
| Филтри | Период, локация, статус, сума. | Да | Филтрите не променят данни. |
| Детайл на транзакция | Връзка към локация, сума, статус, отчетен период. | Само преглед | Не се вижда вътрешна risk логика. |

**8.3 Финанси**

| Елемент | Какво се вижда | Действие | Ограничение |
| :---- | :---- | :---- | :---- |
| Месечни справки | Оборот, договорен процент, задължение, платено / неплатено. | Преглед | Без редакция. |
| История на плащания | Период, статус, сума, дата на плащане. | Преглед | Без промяна на статуси. |
| Export | CSV / Excel export за разрешени финансови справки. | Да | Само за собствените данни на партньора. |

**Currency Display:**
- Системата работи в BGN.
- По време на дефиниран BGN→EUR преходен период: сумите се показват едновременно в BGN и EUR.
- След края на преходния период: BGN се скрива; показва се само EUR.

**8.4 Профил и партньорство**

| Елемент | Какво се вижда | Действие | Ограничение |
| :---- | :---- | :---- | :---- |
| Основна информация | Име на бизнес, контакти, категории, локации, меню линк. | Ограничено | Критични данни минават през заявка за промяна. |

| Маркетингов консент | Съгласие за партньорски комуникации и кампании. | Да | Не влияе върху operational access. |
| Заяви промяна | Заявка за промяна на данни, локации или параметри. | Да, чрез заявка | Промяната влиза за review в admin панела. |

| Елемент | Какво се вижда | Действие | Ограничение |
| :---- | :---- | :---- | :---- |

| Моите заявки | История на собствените заявки. | Преглед | Не се виждат чужди заявки. |

| Комуникация по заявка | Съобщения и история към конкретна заявка. | Да | Партньорът вижда само съобщенията по собствените си заявки. Статусът се управлява от BoomCard. |

**9\. Комуникация, имейли и ticketing**

Избраният communication model е **Hybrid (email inbound + form inbound → unified request system)**.

| Канал | Как работи |
| :---- | :---- |
| Имейл до office@boomcard.bg | Email gateway parse-ва входящия имейл и създава request в системата. Изпраща се auto-reply към подателя с numeric request reference number. |
| Форма в Partner панел (Помощ \> Нова заявка) | Директно създава request в системата. |

**Routing и assignment — изцяло ръчно:**

* Всички входящи заявки (от имейл и от форма) влизат автоматично в споделена "Unassigned" опашка, видима за всички администратори.  
* Всеки администратор може да поеме заявка.  
* Super Admin може да преназначи вече поета заявка.

**Задължителни изисквания за всяка заявка:**

* Всяка заявка има статус, история, собственик, assignee и пълна проследимост.  
* office@boomcard.bg е нотификационният и комуникационен канал за партньорски заявки.  
* support@boomcard.bg е inbound каналът за user support и admin support.

**10\. Матрица на разрешенията**

| Действие / данни | Партньор | BoomCard admin | Бележка |
| :---- | :---- | :---- | :---- |
| Преглед на KPI | Да | Да | Партньорът вижда само своите данни. |
| Преглед на транзакции | Да | Да | Партньорът вижда само свои транзакции. |
| Редакция на транзакции | Не | Да | Само през admin logic. |
| Промяна на процент | Не | Да | Минава през договорна / admin процедура. |
| Промяна на QR код | Не | Да | Управлява се от admin панела. |
| Промяна на локации | Само чрез заявка | Да | Не е директна редакция. |
| Маркетингов консент | Да | Да | Партньорът може да го включва и изключва. |
| Support заявка | Да | Да | Партньорът вижда само собствените си заявки. |
| Закриване на акаунт | Само чрез заявка | Да | 30-дневен notice period. |

| :---- | :---- |
