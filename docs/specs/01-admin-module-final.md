# **1\. Цел, стандарти и принципи**

### **1.1 Цел**

Супер админ панелът е централната работна среда на BoomCard. Той осигурява пълен контрол върху User, Partner и Admin accounts, партньорите, финансите, риска и оперативната конфигурация на системата.

### **1.2 Основен UX принцип**

Dropdown менюто трябва да бъде кратко и да съдържа главни категории. Детайлните таблици, филтри, бутони и действия се отварят вътре в съответната категория. Така менюто остава чисто, а системата остава мащабируема.

# **3\. Табло**

Таблото е първият екран след вход. То не е тежка аналитика, а контролен център за бърза ежедневна ориентация. Целта е супер админът за няколко секунди да разбере дали има проблем, къде трябва да действа и кои процеси изискват внимание.

## **3.1 Обзор**

| Блок | Показатели | Причина |
| :---- | :---- | :---- |
| Абонати | Активни User accounts, нови User accounts, accounts със subscription status, който не позволява сканиране на бележки | Бърз поглед върху потребителската база. |
| Транзакции | Брой транзакции днес, общ оборот, средна стойност | Контрол върху реалната употреба на системата. |
| Кешбек | Начислен, Cleared, Pending и Expired cashback | Контрол върху бъдещи задължения към абонати. |
| Партньори | Активни партньори, нови заявки, активни локации | Поглед върху партньорската мрежа. |
| Финанси | Плащания за изпълнение, очаквани суми от партньори, марджин | Бърз финансов контрол. |

## **3.2 Сигнали и известия**

| Тип | Примери | Къде води |
| :---- | :---- | :---- |
| Критични | Рискови транзакции, неуспешни плащания, системни грешки, подозрителна активност | Към Контрол или Финанси. |
| Оперативни | Нови партньорски заявки, User accounts достигнали payout праг, транзакции и cashback records, чакащи review | Към Партньори, Абонати или Финанси. |
| Информационни | Нови регистрации, активирани партньори, завършен онбординг | За кратка дневна ориентация. |

Всеки сигнал трябва да бъде кликаем. Например сигнал за нови партньорски заявки води към Партньори \> Заявки, а сигнал за рискови транзакции води към Контрол \> Преглед на рискови транзакции.

# **4\. Абонати**

Абонати е централното място за управление на User accounts, профилите, абонаментите, транзакциите и cashback баланса. Account и Profile са отделни слоеве: account управлява достъпа и status, а profile съдържа data и settings.

## **4.1 Всички абонати**

Списъкът трябва да показва всички User accounts и техните профили, включително accounts със status Active, Inactive и Archived. Archived е historical status, при който се пазят history, payments и transactions.

| Елемент | Обяснение |
| :---- | :---- |
| User ID | Уникален идентификатор на User account. |
| Име, имейл, телефон | Основни данни за контакт. |
| Статус | Active, Inactive, Archived. |
| Риск | Рисков профил на база поведение. |
| Последна активност | Последно действие в приложението. |

## **4.2 Абонаменти**

| АКТУАЛИЗИРАНО |
| :---: |

Профилът и абонаментът са отделни слоеве. Един потребител може да има история от различни абонаменти във времето. Трябва да се виждат тип план, период, плащания, статус и история.

| Елемент | Обяснение |
| :---- | :---- |
| Basic | Базов план. |
| Premium седмичен | Седмичен Premium план. |
| Premium месечен | Месечен Premium план. |
| Статус | Active, Expired, Cancelled, Failed Payment. |
| Неуспешно плащане – единичен опит, без защитен период При наближаване на дата на подновяване системата прави един и единствен опит за таксуване (автоматично при включен auto-renew или ръчно при потребителско действие). Ако опитът е неуспешен, абонаментът преминава в статус „неуспешно плащане“ в деня на изтичане. Това НЕ е защитен период – няма retry прозорец и няма повторни автоматични опити. Функцията „сканиране на бележки“ се блокира незабавно. В мобилното приложение на мястото на функцията се визуализира CTA за плащане и активация на абонамента. Потребителят може да възобнови абонамента си през CTA или през меню Абонамент и плащания. |  |

### **Ефект върху съществуващ кешбек при неуспешно плащане**

| Кешбек статус | Поведение при неуспешно плащане | Бележка |
| :---- | :---- | :---- |
| Pending | Остава Pending до review решение. Pending не участва в payout threshold, available balance, payout process или expiry countdown. | 60-дневният rolling срок започва само ако cashback record премине към Cleared. |
| Cleared | Остава Cleared. 60-дневният rolling срок продължава по нормалния си график от датата на Cleared. | Видим в админ панела и User профила. |
| Paid | Не се променя. Paid означава, че payout process е стартиран. | Expiry countdown е inactive. |

Правило за нови cashback records: не се генерират нови cashback records, докато subscription status не позволява сканиране на бележки, защото сканирането на бележки е блокирано.

## **4.3 Транзакции**

Транзакциите се създават след QR сесия, плащане и качване на касова бележка през мобилното приложение. Всяка транзакция трябва да има връзка към User account, Partner account, локация, бележка, cashback record и risk level.

| Елемент | Обяснение |
| :---- | :---- |
| Transaction ID | Уникален номер на транзакцията. |
| Дата и час | QR сесия и качване на бележка. |
| Партньор | Обектът, към който се отнася транзакцията. |
| Сума | Стойност от бележката. |
| Cashback | Изчислена сума към User account. |
| Марджин | Вътрешна печалба на BoomCard. |

## **4.4 Кешбек**

| АКТУАЛИЗИРАНО |
| :---: |

Cashback се управлява record-based, защото всяка сума има собствен 60-дневен rolling срок. Само Cleared cashback участва в payout threshold. Pending cashback няма active expiry countdown.

| Статус | Описание | Видимост за потребителя |
| :---- | :---- | :---- |
| Pending | Очаква automatic approval или manual review решение. | Да – като „Чакащ“ / „В процес на проверка“. |
| Cleared | Одобрен и валиден cashback record. 60-дневният rolling срок започва от датата на Cleared. | Да – като „Наличен“ с „валиден до“. |
| Paid | Payout process е стартиран. Това означава, че cashback е изпратен за изплащане, а не че банковото получаване е финално потвърдено. | Да – като „Изпратен за изплащане“ / „Изплатен“ в историята. |
| Expired | Изтекъл Cleared cashback record, който не е преминал към Paid в рамките на валидността. | Да – като „Изтекъл“. |
| Voided | Анулиран cashback record с причина. | Да – като „Анулиран“ с visible причина. |
| Pending cashback при risk reviewPending cashback за транзакция, попаднала в risk review, остава видим за потребителя до финализиране на проверката. Ако транзакцията бъде одобрена, Pending record преминава към Cleared и 60-дневната валидност започва от датата на Cleared. Ако транзакцията бъде отхвърлена, Pending record преминава към Voided и остава видим в историята със статус „Анулиран“ и причина. Voided е terminal status. Решението се записва в history с отговорник, timestamp, reason category и internal note при нужда. |  |  |

| Етап | Какво се случва | Достъп за партньор |
| :---- | :---- | :---- |

| Одобрен за activation | Onboarding е валидиран за качество и консистентност. Admin / Account Manager генерира activation link. | Read-only до клик на activation link; след activation account става Active. |

# **6\. Финанси**

## **6.1 Плащания към абонати**

| АКТУАЛИЗИРАНО |
| :---: |

User получава право на payout след достигане на минимален праг според плана. IBAN field съществува в User profile, но не е задължително при регистрация. При достигане на payout threshold системата изисква попълнен IBAN, ако липсва. След въвеждане IBAN остава записан в profile и се използва за следващи payouts, докато User не го промени ръчно. Когато payout threshold е достигнат и има валиден IBAN, системата стартира payout process автоматично.

| Елемент | Обяснение |
| :---- | :---- |
| Payout process | Автоматично стартиране на payout при достигнат threshold и наличен IBAN. |
| IBAN | Profile-level field, въведен от User. Не е задължителен при регистрация, но е задължителен за payout. |
| Status | Paid означава, че payout process е стартиран. |
| Failed payout handling | При първи failed payout заради грешен IBAN User получава notification да провери и коригира IBAN. При втори failed payout същият cashback record се връща за manual review с High risk и internal note/history. |
| Subscription gate | User трябва да има subscription status, който позволява payout при достигане на payout threshold. Paid cashback record продължава payout process независимо от последваща промяна на subscription status. |

## **6.2 Фактуриране към партньори**

Партньорите се фактурират на база договорения процент върху одобрените транзакции. Вътрешната разбивка между кешбек към абонат и марджин за BoomCard не се показва на партньора.

| Елемент | Обяснение |
| :---- | :---- |
| Оборот | Сума на одобрените бележки. |
| Процент | Договорена отстъпка. |
| Задължение | Сума за фактуриране. |
| Платено | Проследяване на плащането. |

## **6.3 Отчетни периоди**

Месецът трябва да може да се затваря. След заключване на период данните за фактуриране не се променят свободно.

## **11.2 Email-to-request threading**

Email parser-ът трябва коректно да разпознава нови requests и отговори по съществуващи requests, за да не се създават дубликати при всеки email reply. Долната логика описва request threading-а.

### **Изходящи имейли от системата – маркиране**

Всеки имейл, изпращан от системата по съществуващ request (auto-reply при създаване, отговор от admin, notification за смяна на status), трябва да съдържа:

| Маркер | Място | Формат и предназначение |
| :---- | :---- | :---- |
| Request reference number в subject | Email subject line | Numeric-only reference number във формат \[\#1234\] преди оригиналното заглавие. Това е visible marker за получателя и fallback signal за parser-а. |
| X-BoomCard-Request-ID header | Hidden email header | Технически идентификатор: X-BoomCard-Request-ID: 1234\. Primary signal за parser-а – по-надежден от subject parsing. |
| Message-ID и In-Reply-To headers | Standard RFC 5322 headers | Стандартните email threading headers. Всеки изходящ имейл получава уникален Message-ID, всеки reply от системата ползва In-Reply-To със стойност на оригиналния Message-ID. |
| Reply-To адрес | Reply-To header | Конкретен адрес за request във формат request-1234@boomcard.bg, ако се имплементира plus-addressing, или support@/office@ според configured inbound logic. |

### **Входящи имейли – логика за свързване**

При получаване на имейл parser-ът следва приоритетна последователност за определяне дали имейлът е нов request или reply по съществуващ request:

| Приоритет | Проверка | Действие при match |
| :---- | :---- | :---- |
| 1 (highest) | X-BoomCard-Request-ID header присъства и е валиден. | Прикачи имейла към съответния request като нов message в историята. |
| 2 | In-Reply-To или References header съвпада с Message-ID на изходящ системен имейл. | Прикачи имейла към request-а, който е генерирал оригиналния имейл. |
| 3 | Reply-To адрес съдържа request marker, ако е имплементиран plus-addressing, напр. request-1234@. | Прикачи към съответния request. |
| 4 | Subject съдържа \[\#XXXX\] pattern с валиден numeric request reference number. | Прикачи към съответния request. Fallback за случаи когато headers са филтрирани. |
| 5 (fallback) | Никой от горните маркери не съответства на съществуващ request. | Създай нов request. Source \= email gateway. Subject на request-а \= subject на имейла без \[\#XXXX\] префикс. |
| Защита срещу spoofing и грешни match-овеParser-ът трябва да валидира, че подателят на reply имейла е owner или assignee на request-а, или е в списъка с разрешени участници. Reply от непознат адрес НЕ се прикача автоматично – вместо това се създава нов request с reference към оригиналния. Това предотвратява опити за инжектиране на съобщение в чужд support диалог. |  |  |

### **Edge cases, които parser-ът трябва да обработва**

* Имейл клиент е премахнал \[\#1234\] от subject. → Headers остават основен сигнал.

* Препратен имейл (Fwd:) от трета страна. → Headers не match-ват. → Създава се нов request.

* Reply на request в status Closed. → Не се отваря старият request. Създава се нов request с reference към предходния, когато е приложимо.

* Bulk reply / out-of-office auto-replies. → Parser-ът разпознава Auto-Submitted: auto-replied header и не създава message, само internal note при нужда.

* Bounce notifications (delivery failures). → Не създават request, но се записват в history/internal notes и при повторение се уведомява assignee, че адресът е невалиден.

# **14\. Чеклист за техническо изпълнение**

* Hybrid communication модел: email и forms са входящи канали; реалната обработка е през unified request system.

* Email parser-ът thread-ва reply-та чрез X-BoomCard-Request-ID header, In-Reply-To header, plus-addressing и \[\#XXXX\] subject pattern. Spoofing protection чрез валидация на подател.

* Матрицата на правата за account statuses Active / Inactive / Archived е source of truth за access control.

* Activation links за partners са валидни 72 ч. Resend е admin-only. Всеки нов link инвалидира предходния.

* User verification links са валидни 24 ч. Password reset links се използват за възстановяване/смяна на парола и archived reactivation.

* Support, disputes и change requests живеят в една request system, разделени с поле „тип заявка“ и priority.

* Няма защитен период при неуспешно subscription payment. Единичен опит, при неуспех – сканирането се блокира с CTA.

* Pending cashback при risk review остава видим. При отказ – Voided с visible причина и history.

* QR кодовете автоматично се деактивират при Partner status Inactive / Archived.

* Партньорският панел показва read-only QR списък със статус.

* Default език за партньори: български без toggle. i18n placeholder да е готов архитектурно.

* Брой обекти dropdown: 1 / 2-5 / 6-10 / 11+.

* Cadence напомняния за изтичащ абонамент: 3 дни / 1 ден / в деня на изтичане.

* Всички request actions, risk decisions, status changes и link resend-и се записват в history / internal notes според случая.

* Permission-based архитектура с module-based permissions – super admin задава права по modules и access levels за всеки Admin account.
