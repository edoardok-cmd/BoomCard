## 1. Плащания – процеси и тестове

### 1.1 Текуща архитектура

| Компонент | Технология | Статус |
|-----------|-----------|--------|
| Основен gateway | Paysera Checkout API v1.6 | Интегриран |
| Алтернативен gateway | Stripe (cards, subscriptions) | Интегриран |
| Абонаментни планове | STANDARD (безплатен), PREMIUM (€9.99/мес), PLATINUM (€19.99/мес) | Дефинирани |
| Wallet система | BGN, top-up, cashback, refund | Изградена |
| Webhook обработка | Paysera callback + Stripe webhooks | Имплементирана |
| Мобилни плащания | Expo WebBrowser → Paysera → deep link redirect | Работещ |

### 1.2 Сценарии за тестване на плащания

#### A. Trial период (ако е активиран)

| # | Сценарий | Стъпки | Очакван резултат | Статус |
|---|----------|--------|------------------|--------|
| T1 | Стартиране на trial | Регистрация → избор на PREMIUM → trial | Subscription status = TRIALING, няма таксуване | ☐ |
| T2 | Trial → активен абонамент | Изчакване на trial_end | Автоматично таксуване, status → ACTIVE | ☐ |
| T3 | Отмяна по време на trial | Cancel преди trial_end | Status → CANCELLED, без таксуване | ☐ |
| T4 | Trial с невалидна карта | Trial_end + declined card | Status → PAST_DUE, retry logic | ☐ |

#### B. Автоматично таксуване (recurring billing)

| # | Сценарий | Стъпки | Очакван резултат | Статус |
|---|----------|--------|------------------|--------|
| R1 | Месечно таксуване | currentPeriodEnd настъпва | Нов invoice, успешно плащане, нов период | ☐ |
| R2 | Годишно таксуване | Yearly billing, period end | Коректна сума (с 20% отстъпка), нов период | ☐ |
| R3 | Failed payment retry | Declined card при renewal | PAST_DUE status, retry на 1/3/7 ден | ☐ |
| R4 | Upgrade mid-cycle | PREMIUM → PLATINUM | Proration изчислен коректно | ☐ |
| R5 | Downgrade mid-cycle | PLATINUM → PREMIUM | Промяна от следващия период | ☐ |

#### C. Анулиране и възстановяване

| # | Сценарий | Стъпки | Очакван резултат | Статус |
|---|----------|--------|------------------|--------|
| C1 | Cancel at period end | Потребител натиска Cancel | cancelAtPeriodEnd = true, достъп до края | ☐ |
| C2 | Cancel immediately | Admin force cancel | Незабавно прекъсване, prorated refund | ☐ |
| C3 | Refund - пълен | Admin инициира full refund | Transaction REFUND, wallet credit | ☐ |
| C4 | Refund - частичен | Partial refund request | Коректна сума, wallet update | ☐ |
| C5 | Re-subscribe след cancel | Потребител се абонира отново | Нов subscription, чист старт | ☐ |

#### D. Paysera-специфични тестове

| # | Сценарий | Стъпки | Очакван резултат | Статус |
|---|----------|--------|------------------|--------|
| P1 | Успешно плащане | Create → redirect → pay → callback | status=1, wallet credited | ☐ |
| P2 | Отказано плащане | Cancel на Paysera страницата | Cancel redirect, status unchanged | ☐ |
| P3 | Callback verification | Paysera изпраща callback | MD5 signature валидиран, OK response | ☐ |
| P4 | Duplicate callback | Същият callback 2 пъти | Идемпотентна обработка, без дублиране | ☐ |
| P5 | Test mode → Production | Превключване PAYSERA_TEST_MODE=false | Реални транзакции преминават | ☐ |
| P6 | Wallet top-up (mobile) | Top-up от мобилното приложение | WebBrowser → Paysera → deep link → balance update | ☐ |

#### E. Edge cases

| # | Сценарий | Стъпки | Очакван резултат | Статус |
|---|----------|--------|------------------|--------|
| E1 | Timeout при плащане | Потребител затваря browser | Status polling открива състоянието | ☐ |
| E2 | Network failure mid-payment | Прекъсване на връзката | Graceful error, retry възможност | ☐ |
| E3 | Валутна конверсия | EUR → BGN | Коректен курс, правилна сума | ☐ |
| E4 | Concurrent payments | Два плащания едновременно | Wallet lock предотвратява race condition | ☐ |
| E5 | Минимална/максимална сума | 0.01 EUR и 10,000 EUR | Валидация работи коректно | ☐ |

### 1.3 Чеклист за production-ready плащания

- [ ] Paysera production credentials конфигурирани (`PAYSERA_PROJECT_ID`, `PAYSERA_SIGN_PASSWORD`)
- [ ] `PAYSERA_TEST_MODE=false` за production
- [ ] Stripe production API keys (ако се използва Stripe)
- [ ] Webhook URL-та регистрирани в Paysera dashboard
- [ ] Webhook URL-та регистрирани в Stripe dashboard
- [ ] SSL сертификат валиден за callback URL-та
- [ ] Тестово реално плащане завършено успешно (€1-2 тест)
- [ ] Refund на тестовото плащане завършен
- [ ] Wallet balance коректен след всички операции
- [ ] Payment failure alert конфигуриран в Sentry
- [ ] Transaction logging работи за audit trail
- [ ] PCI DSS compliance потвърден (Paysera/Stripe обработват карти → SAQ A)

```

├── Virtual Users: 50 concurrent
├── Duration: 10 минути

    ├── GET  /api/health           (100 req/s)

├── Virtual Users: 200 concurrent
├── Duration: 5 минути
├── Ramp-up: 1 минута
└── Целеви метрики:
    ├── p95 response time < 500ms
    ├── p99 response time < 2s
    ├── Error rate < 1%
    └── No memory leaks (heap stable)

Stress Test:
├── Virtual Users: 500 concurrent
├── Duration: 3 минути
├── Цел: Намиране на breaking point
└── Мониторинг:
    ├── CPU usage
    ├── Memory usage

├── Virtual Users: 20 concurrent
├── Duration: 5 минути
└── Сценарий:
    ├── Create payment intent
    ├── Process webhook callback
    ├── Wallet credit
    └── Verify: Няма загубени транзакции
```

## 3. Онбординг на тестови партньори (5-10)

### 3.1 Цели на тестовия онбординг

1. **Валидиране на данни** – дали партньорският профил се попълва коректно
2. **UX feedback** – дали процесът е интуитивен за реални бизнеси
3. **Стикер тестване** – дали BOOM стикерите работят в реална среда
4. **Receipt обработка** – дали OCR разпознава реални касови бележки
5. **Cashback flow** – дали cashback-ът се кредитира правилно

### 3.2 Процес за тестови онбординг

```
Стъпка 1: Подписване на споразумение
├── NDA (ако е необходимо)
├── Тестово споразумение (без финансови ангажименти)
└── Определяне на контактно лице

Стъпка 2: Заявка за данни
├── Име на бизнеса (BG + EN)
├── Категория (ресторант, кафене, хотел, магазин, и т.н.)
├── Описание (BG + EN)
├── Лого (мин. 400x400px, PNG/JPG)
├── Cover image (мин. 1200x600px)
├── Адрес + GPS координати
├── Работно време
├── Телефон, имейл, уебсайт
├── Контактно лице

Стъпка 3: Въвеждане в системата
├── Създаване на Partner запис (status: PENDING)
├── Създаване на Venue запис(и)
├── Създаване на 2-3 тестови оферти
├── Генериране на BOOM стикер QR кодове
└── Качване на лого и cover image в S3

Стъпка 4: QA ревю
├── Проверка на данните за коректност
├── Визуална проверка на офертите
├── Тест на стикер сканирането
├── Тест на receipt обработката
└── Активиране (status: ACTIVE)

Стъпка 5: Тестов период (2 седмици)
├── Реално сканиране на стикери от тест-потребители
├── Submit на реални касови бележки
├── Събиране на feedback (форма или интервю)
└── Документиране на бъгове и проблеми

Стъпка 6: Обратна връзка
├── Structured feedback форма
├── UX проблеми → backlog
├── Data issues → корекции
└── Решение: продължава / напуска пилота
```

### 3.3 Критерии за избор на тестови партньори

| Критерий | Защо е важен |
|----------|-------------|
| Физическо местоположение в София | Лесен достъп за стикер тестване |
| Активен бизнес с клиенти | Реални касови бележки |
| Технически грамотен собственик | По-качествен feedback |
| Различни категории | Тестване на разнообразни сценарии |
| Готовност за feedback | Ангажираност с процеса |
| Средно 50+ клиента на ден | Достатъчен обем за тестване |

```
- Разработка (ако outsource)
- Маркетинг и реклама
- Офис / coworking (ако е приложимо)

ВАЖНО: Paysera fees и Stripe fees → разход, приспадан от приходи
```
